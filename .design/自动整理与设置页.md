# 自动整理与插件设置页（设计稿）

> **状态**：**Draft**（2026-10-17）。这是一条**决策反转 + 新能力**的提案，等所有者确认
> §8 的三个未决问题后，才升级为 Baseline 并进入实现。
>
> 需求来源（所有者 2026-10-17 原话，两件事一起提的）：
> 1. `mdRoot` **默认 `~/OblivionKB`，但要在插件里能自定义路径**；
> 2. **插件能自动整理文本内容**，且「增加使用 DSH 中可复用的 API 地址和密钥」，
>    「这个要在插件的设置里能**选择想用的模型**和**自动切换**功能」。

---

## 1. 要反转的那条决策

设计书与代码里一直写着一条约束：**「插件不调 LLM」**。它的原话在
[`oblivion-core/README.md` §五 偏离 4](../oblivion-core/README.md)（旧版）与
[`src/digest/index.ts`](../oblivion-core/src/digest/index.ts) 的注释里，理由是当时「`ctx.llm` 的
稳定调用面未确认」，于是判定与整理**全部走确定性实现**（token Jaccard + 规则打分）。

**这条理由现在被证伪了**（见 §3：真实 API 核对结果）。所以本设计要做的第一件事是
**把「插件不调 LLM」从「硬约束」降级为「默认行为」**：

- 默认**仍然**确定性、不联网、不发任何外部请求；
- 只有在设置页**显式开启**并选定模型后，才调 LLM。

**这条反转本身要一条正式决策记录**（DEC），编号与落点见 §8 问题 3。

---

## 2. 需求拆成两件，不要混在一起

| | 能力 | 落点 | 依赖 |
| --- | --- | --- | --- |
| **A** | 知识库根路径**可在插件里自定义** | 设置页（写配置）+ core 读取 | 无外部依赖，纯配置 |
| **B** | **自动整理文本内容**（标题/标签/摘要/归档） | core 新增 `src/organize/`；设置页只做「开关 + 选模型」 | `ctx.llm` + `ctx.credentials` |

两件事可以**分两次交付**：A 是配置读写，风险低；B 是外部调用，风险高、必须默认关。

## 3. 实测可用的宿主接口（这一节是设计的全部依据）

> 来源：对已装宿主 `@deepseek-ai/*`（`~/.dsh/profiles/node_modules` 里的 junction → 宿主 bundle）
> 的只读核对，2026-10-17。核对结论已同步回 [`oblivion-core/README.md` §五 偏离 4](../oblivion-core/README.md)。

**能用的**：

| 要什么 | 用什么 | 出处 |
| --- | --- | --- |
| 列出已配置的 provider | `ctx.llm.listProviders()` → `{ id, name }[]` | `dsh-llm/lib/types/index.d.ts` |
| 列（含未激活的）provider | `ctx.llm.listConfigurableProviders()` | 同上 |
| 列某个 provider 的模型 | `ctx.llm.listModels(provider)` → `{ provider, id, name, … }[]` | 同上 |
| 模型细节 | `ctx.llm.resolveModelInfo(provider, model, signal?)` | 同上 |
| **发起一次调用** | `ctx.llm.stream({ provider, model, messages, system?, maxTokens?, temperature?, signal? })` → `AsyncIterable<StreamChunk>` | 同上 |
| 收流拼结果 | `BlockAssembler`（`@deepseek-ai/dsh-llm`）：`push(chunk)` / `blocks()` / `finish` / `usage` | `dsh-llm/lib/types/assembler.d.ts` |
| **取密钥** | `(await ctx.credentials.resolve(credentialRef('DEEPSEEK_API_KEY')))?.value` | `dsh-credentials` |
| **默认选路** | `ctx.agentDefaultModel.currentSelection()` → `{ provider, model }` | `dsh-agent-default-model` |
| **取 baseURL** | `ctx.settings.describe()` 里 pi-ai 命名空间的 `value.providers.<p>.baseURL` | `dsh-settings` |

**没有的**（别按想象中的 API 写）：

- **没有** `ctx.llm.chat()` / `complete()` / OpenAI 兼容的现成客户端 —— 只能 `stream()` 自己收；
- **没有** `ctx.model` / `ctx.provider` / `ctx.providerRegistry` 这类服务；
- baseURL **不在** `ctx.llm` 的 provider 信息里，要经 `ctx.settings.describe()`（注意它**脱敏**，
  secret 字段回来是打码的）或直接读 profile patch 文件。

**官方范例**（照抄它的骨架）：`@deepseek-ai/dsh-session-title-llm` ——
`createUserMessage(...)` → `ctx.llm.stream(options)` → `for await` 喂 `BlockAssembler` → `blocks()`。

**不引入新运行时依赖**：core 现在刻意用**结构化类型**描述 `ctx`（见 `src/core-types.ts` 顶部注释），
所以本设计**不 import `@deepseek-ai/dsh-llm`**：

- `messages` 直接传 `[{ role: 'user', content: [{ type: 'text', text }] }]`（一次性调用，无需 `createUserMessage`）；
- 收流用一个**极小的文本累加器**（只关心 text delta）代替 `BlockAssembler`；
- 需要时再在 `package.json` 的 `dsh.compat.requires.hostPackages` 里声明（见 §7）。

## 4. 配置分层（问题 A 的关键设计）

「设置页能改路径」要求配置**可被 UI 写入**。现状是：`resolveConfig()` 只吃
**插件 config**（profile patch 里的 `config:` 段），而 profile patch 是**手写 YAML**，
让 UI 去改它既脆弱又危险（那文件里还有别的插件、还有注释与多次备份）。

**提案：加一层 UI 可写的配置层。**

```
优先级（低 → 高）：
  ① DEFAULT_CONFIG（src/config.ts，代码默认值）
  ② 插件 config（profile patch 的 `- id: '@oblivion/core'` 的 config 段）—— 机器/团队权威
  ③ <dataRoot>/settings.json（设置页写入）—— 覆盖 ②，因为「我在界面里改了」必须立刻生效
```

- 读：`resolveConfig()` 先并 ①，再并 ②，最后并 ③；
- 写：**只有**设置页写 ③（原子写，复用现有「临时文件 → rename」）；
- 面板**显示生效值 + 来源**（`默认` / `profile 配置` / `设置页`），
  否则「改了没反应」会变成一个查不出来的 bug。

> 为什么 ③ 压过 ②：如果 profile 赢，用户「在界面里改了路径却什么都没发生」——
> 这是最糟的交互。反过来，profile 只作为**新机器的种子**，一旦用户在界面里表态，就以界面为准。

## 5. 设置项（进 `config` 也进设置页）

```yaml
# 现有
mdRoot: '~/OblivionKB'          # ← 问题 A：设置页可直接改

# 新增（问题 B）
organize:
  enabled: false                # 默认关 —— 不显式开就一个请求都不发
  digest: true                  # 作用域一：会话整理（oblivion_digest）的产出走模型
  retitle: true                 # 作用域二：知识库级标题/标签回填走模型（先出预览再落地）
  provider: ''                  # 空 = 用 ctx.agentDefaultModel.currentSelection()
  model: ''                     # 空 = 同上；设置页从 ctx.llm.listModels(provider) 里选
  fallbacks:                    # 「自动切换」：按序尝试
    - { provider: 'deepseek', model: 'deepseek-chat' }
  maxTokens: 1024
  timeoutMs: 30000
  trigger:
    everyTurns: 0               # 0 = 不自动触发；N>0 = 每 N 个 turn/end 触发一次
    minIntervalMs: 600000       # 同一会话两次整理的最小间隔（10 分钟）
```

**「自动切换」的语义**（这是所有者明确点名的功能）：按 `provider/model` → `fallbacks[0]`
→ `fallbacks[1]` … 顺序尝试；某次调用失败（额度 / 网络 / 4xx / 超时）就**切下一个**；
全失败则记一条判定留痕（复用 `stats`）并**放弃本次整理**，绝不阻塞 turn。
设置页里 `fallbacks` 是个可增删的模型列表。

## 6. 零侵入怎么保持

现有约束是「不阻塞主链路、无 cron / Worker / 定时器，保留期与图衰减都是**读取时惰性计算**」。
自动整理必须守住这条：

- **触发点**：`turn/end` 之后**异步**跑（`void` + 内部 try/catch + 超时），
  绝不 `await` 在事件处理里；
- **节流**：`trigger.everyTurns` + `trigger.minIntervalMs` 双闸门，且同一会话**串行**（一次只有一个在跑）；
- **默认关**：`organize.enabled: false` ⇒ 连 `ctx.llm` 都不注入使用；
- 不需要新服务、不注册定时器 ⇒ 仍然是「一个 turn/end 触发 + 惰性读」。

## 7. 需要向宿主声明的东西

`package.json` 的 `dsh.compat.requires` 要加：

```jsonc
"services": ["tools", "systemPrompt", "llm", "credentials"]
```

（现在只有前两个。）不加 `llm` / `credentials` 就拿不到这两个服务；
用 Cordis 的 `inject` 声明，缺服务时**优雅降级**（设置页显示「宿主未提供 llm 服务」），
而不是让整个 `apply()` 抛错 —— 这正是 2026-10-17 那次「工具重复注册」踩到的教训（见 §9）。

## 9. 顺带要修的（本稿之外，但同一主题）

2026-10-17 改 profile 配置时暴露的一个**真实缺陷**，已记进本轮汇报，需单独修：

> core 的 `apply()` 把工具注册挂在 **根上下文**（`ctx.root`）上且**没有 disposer**，
> 而根上下文**比 core 的 fiber 活得久** ⇒ **重新装载（改 profile 配置就会触发）时
> 第二次 `ctx.tools.register('oblivion_capture')` 会抛
> 「already registered」**，症状是 core 整个 `apply:failed`、MCP 通道从桥接里消失
> （`slots: 0`）。修法：让 `registerTools()` 收集每次注册的 disposer 并返回一个聚合
> disposer，由 `applyInner()` 包进 `ctx.effect(...)`；或改为注册在 core 自己的 `ctx` 上并
> 确认分层视图仍可见。**这条修完前，别在 DSH 运行时改 core 的 profile 配置。**

## 10. 验收（Baseline 之后才有意义，先列出来定预期）

- **A（路径）**：设置页改 `mdRoot` → 取消/重启后 core 读到的是新值；面板显示来源；非法路径被拒。
- **B（自动整理）**：
  - `enabled: false` 时，**抓包/计时证明零外部请求**；
  - 开启并选定模型后，`turn/end` 达到阈值 → 产出确实被模型整理过（可对比确定性版本）；
  - **断网 / 关掉主 provider** → 自动切到 `fallbacks[0]`，留痕里能看到切换过程；
  - 全部失败 → turn 不受影响，留痕记「本次整理放弃」。
