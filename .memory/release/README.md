# .memory/release/ — 三级版本分层日志

> **本目录不入库**（`.gitignore` 的「本地协作层」段）。它是本机的发布流水，
> 面向公开发布的版本说明写进仓库根的 [`../../CHANGELOG.md`](../../CHANGELOG.md)。

版本分层照搬参考架构（DSH）的三级模型，见设计书 §2.2 **O1** 与 §18 **Phase 10**。

## 两条版本轴，别混

| 轴 | 版本号 | 记录在哪 | 变更依据 |
|---|---|---|---|
| **产品版本** | `0.0.1` → `0.1.0` → … | **本目录** + 根 `CHANGELOG.md` | 代码/功能变了 |
| **设计书版本** | `v4.0` → `v4.0.1` → … | `design/architecture.md` §20 | 设计断言变了 |

一次产品发布**可能不改设计书**，一次设计修订**可能不发版**。两条轴各记各的，
混在一起就再也说不清「这个行为是哪个版本引入的」。

## 三级分层

| 级别 | 目录 | 何时写 | 内容特征 |
|---|---|---|---|
| **alpha** | `alpha/` | 每次内部可运行增量 | 增量清单，允许推翻，**不承诺兼容** |
| **rc** | `rc/` | alpha 累积够了，准备对外 | **汇总**：把 alpha 增量合并成一份用户能读的说明 |
| **patch** | `patch/` | rc 之后发现必须修的问题 | **热修**，范围尽可能窄，必须写清影响面 |

**破坏性变更的契约**（RISK-111）：破坏性变更**只在 rc.1 的「其他变更」章节里宣告**，
不允许散落在 alpha 增量里 —— 否则升级的人必然漏看，升完就崩。

## 命名

```
alpha/v0.0.1.md          # 产品版本号，与根 VERSION 一致
rc/v0.1.0-rc.1.md        # rc 用 <版本>-rc.<序号>
patch/v0.1.0-rc.1-p1.md  # 热修用 <被修的版本>-p<序号>
```

## 写记录的时机

1. 改了行为、依赖、持久化格式、CLI 参数 → **必须**写
2. 只改注释、格式、文档措辞 → 不写（`git log` 够了）
3. 修了线上问题 → 写 `patch/`，并在记录里写清**触发条件**，不能只写「修了 bug」

## 已知缺口

`scripts/bump-version.ps1` 目前只同步根 `package.json`，**不会**自动在这里建记录，
也**不会**同步各个能力包的 `package.json` 与 `registry.json`。

后者的漏改由 `tests/unit/version-consistency.test.mjs` 兜底（会直接测试失败）；
前者靠人 —— 因此**递增版本后请手动在这里补一条**。
