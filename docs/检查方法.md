# 插件检查方法

> 本文是 Oblivion 工作区的**检查规范**。新建插件、改动现有插件、DSH 升级后，
> 都按本文执行。它回答一个问题：**这个包现在是不是好的？**
>
> 关联：`tools/check-workspace.ps1`（执行入口）· `tools/run-selfcheck.ps1`（selfcheck 跑批）·
> `.design/DSH-COMPAT.md`（宿主契约）· `WORKSPACE.md`（环境与已知限制）

---

## 一、四层检查，各管一段

工作区的检查不是一个脚本，是四层。**每层抓的故障不同，缺一层就有盲区。**

| 层 | 抓什么 | 入口 | 何时必须跑 |
| --- | --- | --- | --- |
| **① 版本一致性** | `VERSION` 与 `package.json` 漂移 | `node scripts/bump-version.mjs --check` | 每次提交前 |
| **② 类型** | 类型错误、接口不匹配 | `tsc -p tsconfig.json --noEmit` | 每次提交前 |
| **③ 单元测试** | 纯逻辑、边界值、异常输入 | `node --test`（`test/*.test.mjs`） | 每次提交前 |
| **④ 端到端自检** | **产物能否被真实装载**、契约形状、装载副作用 | `node scripts/selfcheck.mjs` | 每次提交前 + **改动装载路径后** |

### 为什么第 ④ 层不可省

前三层验的是**源码**，第 ④ 层验的是**产物 + 装载行为**。它们抓的故障类型完全不同：

| 只有前三层会漏掉的故障 | 实例 |
| --- | --- |
| 产物 import 失败（裸导入解析不了） | `lib/index.js` 里 import 了没标 external 的包 |
| `inject` 声明了宿主没有的服务 | `http-bridge` 初版声明 `webServer` → desktop 停在 pending，**不报错** |
| 导出的形状变了（`apply` 不是函数 / 缺 `provides`） | 重构时漏改 export |
| 契约常量漂移（协议版本、错误码） | 对齐宿主时改错了数字 |
| 装载副作用（该注册的路由没注册 / 该清理的没清理） | `effect` 没返回 disposer → HMR 重载泄漏端口 |
| 配置默认值被改错 | 默认端口从固定值改成随机 |

**2026-10-06 的 App 崩溃、路由数变化、缺失导入，全是第 ④ 层抓出来的。**
所以 `run-selfcheck.ps1` 的注释里写着：它必须进 `check`。

## 二、一条命令跑全部

```powershell
# 工作区统一入口（在运行时解析 DSH 的 node/pnpm，不要求 PATH 上有）
powershell -File tools/check-workspace.ps1

# 等价于：契约校验 → install → typecheck → test → build → 版本一致性 → selfcheck
```

### 分任务跑

```powershell
powershell -File tools/check-workspace.ps1 -Task install     # 安装依赖（工作区一份）
powershell -File tools/check-workspace.ps1 -Task typecheck   # 全部包的类型
powershell -File tools/check-workspace.ps1 -Task test        # 全部包的单测
powershell -File tools/check-workspace.ps1 -Task build       # 全部包的构建
powershell -File tools/check-workspace.ps1 -Task version     # 版本一致性
powershell -File tools/check-workspace.ps1 -Task compat      # DSH 宿主契约（升级后最该跑）

# selfcheck 单独入口（因为 -Task 的 ValidateSet 不含 selfcheck）
powershell -File tools/run-selfcheck.ps1
```

### 单个包

```powershell
$node = "$env:USERPROFILE\.dsh\dsh-runtimes\dsh-primary-runtime\dependencies\node\bin\node.exe"

& $node $pnpm -C oblivion-core run typecheck
& $node $pnpm -C oblivion-core run test
& $node $pnpm -C oblivion-core run selfcheck
& $node $pnpm -C oblivion-core run check:version
```

## 三、新建插件时的检查清单

新包必须凑齐这几样，否则 `check` 会漏过它（`pnpm -r --if-present` 对**没有该 script 的包静默跳过**）。

### package.json 的 scripts

```json
{
  "scripts": {
    "build": "node scripts/build.mjs",
    "typecheck": "tsc -p tsconfig.json",
    "test": "node --test",
    "selfcheck": "node scripts/selfcheck.mjs",
    "version:bump": "node scripts/bump-version.mjs",
    "check:version": "node scripts/bump-version.mjs --check"
  }
}
```

### 目录

```
<plugin>/
├── package.json          # 上面六个 script
├── VERSION               # 版本单一真源
├── tsconfig.json
├── dshx.yml              # id 必须与 package.json 的 name 逐字相同
├── cordis.patch.yml      # 装载声明（热挂）或由 bundle 提供
├── README.md
├── scripts/
│   ├── build.mjs         # esbuild；框架包标 external
│   ├── selfcheck.mjs     # ← 本文第四节
│   └── bump-version.mjs  # 从既有包复制
├── src/                  # TS 源码
├── test/                 # *.test.mjs（node --test）
└── lib/                  # 构建产物（不入库 VERSION）
```

### 两条硬约束

1. **`lib/` 里不许有 `VERSION` 文件** —— `check-workspace.ps1` 的 `Assert-NoLibVersion` 会直接判失败。
   版本号只存 `VERSION` 与 `package.json` 两处，产物里再存一份就是第三个来源。
2. **`.ps1` 必须带 UTF-8 BOM** —— PS 5.1 把无 BOM 脚本按 ANSI 读，中文注释会乱码到解析失败。
   由 `tools/lint-ps1-bom.ps1` 把关。

## 四、怎么写 selfcheck

### 骨架（与 `oblivion-brand` / `oblivion-http-bridge` 一致）

```js
#!/usr/bin/env node
import assert from 'node:assert/strict';
import { fileURLToPath, pathToFileURL } from 'node:url';
import { join } from 'node:path';

const ROOT = fileURLToPath(new URL('..', import.meta.url));
const results = [];
let failed = 0;
let skipped = 0;
const SKIP = Symbol('skip');

async function check(name, fn) {
  try {
    const detail = await fn();
    if (detail === SKIP) {
      skipped += 1;
      results.push(['SKIP', name, '本机不适用']);
      return;
    }
    results.push(['PASS', name, detail ?? '']);
  } catch (error) {
    failed += 1;
    results.push(['FAIL', name, error?.message ?? String(error)]);
  }
}

// 真实 import 产物（不是读源码）
const mod = await import(pathToFileURL(join(ROOT, 'lib', 'index.js')).href);

await check('产物存在且可 import', () => {
  assert.equal(typeof mod.apply, 'function');
  return 'OK';
});

// ... 更多断言

for (const [status, name, detail] of results) {
  console.log(`${status}  ${name}${detail === '' ? '' : `\n        ${detail}`}`);
}
console.log(`\n${results.length} 项，失败 ${failed}，跳过 ${skipped}`);
process.exit(failed > 0 ? 1 : 0);
```

### 设计原则

**① 验产物，不验源码。**
`await import(lib/index.js)` —— 这一步就抓掉了「裸导入解析不了」这类只在实际装载时才暴露的问题。

**② 断言「这个包该证明什么」，不是「代码长什么样」。**

| 包的职责 | 该断言什么 |
| --- | --- |
| 认知层（core） | 端到端：捕获→落库→检索，去重、建图、画像真的生效 |
| 桥接层（http-bridge） | 真起服务器；鉴权三态；**请求穿透到门面**（`serverInfo.version` 来自 core） |
| 客户端（brand/panel/vimc） | 槽位声明与 `dsh.client.inject` 一致；组件能渲染 |
| 组合层（bundle） | 插了哪些包；**没有重复插**自带 patch 的包 |

**③ 契约常量要钉住。** 协议版本、错误码、`inject` 列表、默认端口——这些是跨包约定，
改错了不会报类型错，只会让对接方莫名其妙失败。写成断言，改的时候就必须改测试。

**④ 本机不适用的用 SKIP，不算失败。** 例如「市场没装」时跳过跨包交叉验证。

**⑤ 端到端要真起服务器 / 真写磁盘。** 用桩只能验形状，验不了「真的接通了」。
`http-bridge` 的 selfcheck 会临时监听测试端口、发真实 `fetch`、断言门面被调用，最后调 disposer 收尾。

### 反面教材：断言产物文本时小心压缩

esbuild 压缩后变量声明形式会变。写 `assert.match(bundleText, /port: 42081/)` **会失败**，
因为产物里是 `var DEFAULT_PORT = 42081`。这类断言要对着**实际产物**写，不是对着源码想象。

## 五、DSH 升级后

```powershell
powershell -File tools/check-workspace.ps1 -Task compat
```

这条回答「DSH 升级后我的插件还活着吗」。机制、升级 SOP 与台账见
[`.design/DSH-COMPAT.md`](../.design/DSH-COMPAT.md)。

每个包在 `package.json` 的 `dsh.compat` 里声明自己依赖什么：

```json
{
  "dsh": {
    "compat": {
      "host": ">=0.2.0-rc.2 <0.3.0",
      "requires": {
        "services": ["tools", "systemPrompt"],
        "events": ["agent/created", "session/event", "turn/end"],
        "hostPackages": ["@deepseek-ai/dsh-tools"]
      },
      "provides": { "services": ["oblivion"] }
    }
  }
}
```

**`provides` 是新增字段**（core 0.2.0 起）：声明本包往 Cordis 服务表里注册了什么，
供其他插件 `inject`。检查脚本据此校验「谁提供了什么、谁依赖了它」。

### 三类服务依赖，别用错字段

这是 2026-10-06 踩到的坑，误用会得到**极具误导性**的 FAIL：

| 字段 | 语义 | 取证对象 | 例 |
| --- | --- | --- | --- |
| `requires.services` | DSH **宿主**提供的服务 | DSH 源码 `packages\**\*.ts` | `tools`、`systemPrompt` |
| `requires.workspaceServices` | **同工作区其他包** provide 的服务 | 各包 `dsh.compat.provides.services` | `oblivion` |
| `requires.npmPackages` | 第三方 npm 包（装在 profile） | `~/.dsh/profiles/desktop/node_modules` | `dsh-better-sidebar` |

**误用的后果**：把工作区服务写进 `requires.services`，校验会去 DSH 源码里找 `oblivion`，
当然找不到，报：

```
FAIL  service  oblivion  源码里找不到该服务名
=> FAIL（1/3 项不通过）
结果：升级已破坏契约 —— 按上面的证据逐个修插件。
```

这条 FAIL 看起来像「DSH 升级把契约搞坏了」，**实际只是字段用错了**。
所以 `workspaceServices` 单独成一类断言（`wsService`），证据直接打印提供方：

```
PASS  wsService  oblivion  由 @oblivion/core provides
```

## 六、当前检查台账

> 数据来自 2026-10-06 的全量跑批（`tools/check-workspace.ps1` 全绿）。

| 包 | 版本一致 | typecheck | 单测 | selfcheck | 宿主契约 |
| --- | --- | --- | --- | --- | --- |
| `oblivion-brand` | PASS | PASS | — | PASS (11) | PASS (10/10) |
| `oblivion-bundle` | PASS | — | — | PASS (14) | PASS (7/7) |
| `oblivion-core` | PASS | PASS | PASS (14) | PASS (29) | PASS (9/9) |
| `oblivion-http-bridge` | PASS | PASS | PASS (16) | PASS (14) | PASS (3/3) |
| `oblivion-panel` | PASS | PASS | PASS (14) | PASS (12) | PASS (6/6) |
| `oblivion-vimc` | PASS | PASS | PASS (42) | PASS (15) | PASS (6/6) |

### 剩余缺口

| 缺口 | 风险 | 建议 |
| --- | --- | --- |
| `oblivion-bundle` 无 typecheck | 低 —— 它没有 TS 源码（`lib/index.js` 是手写空壳） | 不补；selfcheck 已覆盖它唯一的实质内容（patch 声明） |
| `oblivion-brand` / `panel` 缺单测 | 低 —— selfcheck 已覆盖主要路径 | 可选：纯逻辑函数改用 `node --test` |

> `pnpm -r --if-present` 对没有该 script 的包**静默跳过**，所以缺检查**不会报错**，
> 只会让你以为「全绿」。新增包或改动脚本时，回来核对这张表。

### 两类「组合层」包的自检要点

`oblivion-bundle` 与 `oblivion-vimc` 的自检证明了两个通用模式，新包可直接照搬：

**① 组合层（bundle）：验的是「声明」，不是「代码」。**
`oblivion-bundle` 没有 `apply()`，它的全部内容是 `cordis.patch.yml`。所以自检做的是：

- 解析 patch 的**实际生效行**（必须逐行剥掉 `#` 注释 —— 注释里也出现包名，
  不剥会被自己的文档骗过去），断言恰好插了 `core` / `panel`；
- **交叉验证**：读工作区里各成员包**真实的** `package.json`，断言
  「被插行的包都不自带 `dsh.bundle.patch`」且「自带 patch 的包没被插行」。
  这一组能抓住「成员包改了交付路径而 bundle 没跟着改」。

**② 客户端插件（client）：三方 id / marker 一致是硬约束。**
`oblivion-vimc` 的自检钉住三处逐字相同：

| 一致项 | 三方 | 漂了的后果 |
| --- | --- | --- |
| **id** | `package.json` 的 `name` · `dshx.yml` 的 `id` · `client.js` 工厂的 `id` | `dshx activate-new-client` 拒绝 |
| **marker** | `dshx.yml` 的 `marker` · `src/index.ts` 的 `console.log` · 产物 | `dshx verify-boot` 静默失败 |

> ⚠️ **两个 `inject` 别混为一谈**（我写第一版断言时就混了，被 FAIL 抓出来）：
> `package.json` 的 `dsh.client.inject` 是**客户端包**依赖；
> `src/client/index.ts` 的 `export const inject` 是 **Cordis 服务**硬依赖。
> 两者正交，各有各的断言。

## 七、常见错误

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `check` 显示全绿但某个包没跑 | 该包缺对应 script，`--if-present` 跳过了 | 对照第三节补齐 scripts |
| `Cannot find type definition file for 'node'` | 包目录没装依赖 | `pnpm install`（在工作区根） |
| selfcheck 里 `import` 报 `ERR_MODULE_NOT_FOUND` | `lib/` 没构建，或 import 了未标 external 的包 | 先 `build`；检查 `scripts/build.mjs` 的 `external` |
| 端到端断言端口冲突 | 测试端口与真实服务撞了 | 用高位端口（如 4209x），用完必须调 disposer |
| 测试跑完进程不退出 | `server.close()` 没被调用 | 确认 `ctx.effect` 返回了 disposer，且测试里调用了它 |
| PS 脚本中文乱码 + 解析失败 | 缺 UTF-8 BOM | 跑 `tools/lint-ps1-bom.ps1` |

## 八、为什么不用 DSHX 的检查

`dshx_check` 等 MCP 工具在**本机全废**：它们先跑 `dshx creator claim`，
而 claim 依赖 POSIX `ps -o lstart=`，Windows 上恒失败（详见 `WORKSPACE.md` 已知限制 1/3）。

但**同样的 check 用 CLI 直接跑是好的**（不经 claim 包装）：

```powershell
$dshx = 'C:\Projects\deepseek-harness\tools\dshx'
node --import "file:///$($dshx -replace '\\','/')/node_modules/tsx/dist/esm/index.mjs" `
     "$dshx\src\cli.ts" check '<插件目录>' --harness 'C:\Projects\deepseek-harness'
```

本工作区的四层检查是**独立于 DSHX 的**，不依赖它的 discover/claim 链路，
所以在 Windows 上始终可用。DSHX 的 CLI check 作为补充，不作为闸门。
