## 回答

用大白话说，**没做完的东西其实只有三堆**，而且它们该由谁来决定、怎么决定，是完全不同的三件事。

## 一、第一堆：差一步就闭合的（一项，我自己就能做）

**R1-f：把「命令行参数」从临时文件改成正式通道。**

现在的做法：你敲 `oblivion web --port 42081`，我就往磁盘写一个临时补丁文件告诉内核端口是多少。这带来一个副作用 —— **运行时数出来 29 层，`--dump-config` 数出来 28 层**，差的正是那个临时文件。

为什么这事必须修：`--dump-config` 是我们唯一的「配置真相来源」。它和实际跑的东西对不上，以后每一次排查都会先怀疑它。

**怎么决定：不用你决定。** 判据是一条等式（两边层数必须相等），成本半天。这是我建议的下一步。

## 二、第二堆：真正的功能空白（大，需要你拍板）

**根子上就一件事：这个软件现在不能对话。**

它有界面、有图标、有令牌、有围栏、有 API 通道 —— 但**没有任何一个能真正干活的插件**。`oblivion web` 启动时那行「等待依赖 13」说的就是这个：13 个插件在等 `llm`、`session`、`knowledge` 这些服务，而这些服务**没有任何包提供**。

要补的顺序是固定的，因为后面的依赖前面的：

| 顺序 | 要补什么 | 补完之后能干什么 |
|---|---|---|
| 1 | **Phase 2**：接一个模型（llm）+ 会话存哪（session）+ API Key 存哪（凭据） | 能真的问一句、答一句 |
| 2 | **MarkdownText**（现在的答案只能显示成纯文本，模型输出是 markdown） | 答案能正常排版显示 |
| 3 | **Phase 3**：知识库 + 文档解析 | 能「上传文档 → 提问 → 沉淀成笔记」闭环 |

**怎么决定：这是你的产品决策，我给判断依据。**

- 如果你要的是「**先让它能用**」→ 做 Phase 2。代价是几天，而且你得先定三件事：**接哪家模型**（DeepSeek 官方？本地 Ollama？）、**API Key 存哪**（设计书写的是 `~/.oblivion/.credentials.yaml`，权限 0600，永不进环境变量 —— 认不认这个方案）、**要不要先只做 CLI 不做界面**（更快）。
- 如果你要的是「**把骨架做到无懈可击**」→ 那就别碰 Phase 2，去做浮层、设置表单、HMR。但我得直说：**骨架的边际收益已经很低了** —— 现在这个壳已经很结实，再加固也不会让它多用一分。

我的看法很明确：**该做 Phase 2 了。** 再加固骨架是在回避真正的问题。

## 四、需要你拍板的，就三件

1. **做不做 Phase 2**（接模型 + 会话 + 凭据）—— 这是「能用的软件」和「漂亮的空壳」的分界。
2. **如果做：接哪家模型、Key 怎么存** —— 我建议先 DeepSeek 官方 + 设计书那套 `~/.oblivion/.credentials.yaml`（0600），因为它最简单且已经有设计依据。
3. **那 23 个空壳包要不要清理** —— 现在 26 个包里只有 3 个有真代码。它们给每个包维护着 package.json + 组合行 + 版本一致性 + 结构契约四份账本，而**防住的 bug 是零**。我的建议是**先不删**：等 Phase 2 做完，就能看清哪些包（`llm-deepseek`、`session-sqlite`…）真的会用上，那时再删剩下确定不会用的，风险最小。

## 五、如果你问我「现在做什么」

**顺序建议：R1-f（半天）→ 那个挂起测试的时间盒（1 小时）→ `cli.ts` 拆分（1 小时）→ 然后开 Phase 2。**

前三个都是「清障」，做完之后你手里会是一个**账目干净、测试可信、文件不臃肿**的骨架 —— 这时再往上加功能，出问题能查得动。如果跳过清障直接开 Phase 2，我担心的是：将来一个 bug 出来，你会同时怀疑「是模型的锅、是会话的锅、还是层账目本来就是错的」。

**要不要我现在就开始 R1-f？** 或者你先告诉我 Phase 2 那三个决定（哪家模型 / Key 存哪 / 先 CLI 还是先界面），我按你的选择排。
