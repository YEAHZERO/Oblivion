# 查看这两个插件，该如何使用 · 轮 14

- 来源会话: `session-67cb0d9e-8043-42cb-81f7-d601e3aa1587`

## 问题

对比这两个：https://github.com/wqty123/dsh-browser，https://github.com/anweat/dsh-browser

## 回答

两个包**不是同一类东西**，而且对你的场景只有一个是"对的"。核心结论先给：**要让 web-search-pro 的浏览器类平台复活，只有 `@anweat/dsh-browser` 有效**——`dsh-builtin-browser` 提供的是另一种服务形状，装上去 web-search-pro 会判定服务不完整。

## 一、定位差异

| 维度 | [anweat/dsh-browser](https://github.com/anweat/dsh-browser) `@anweat/dsh-browser@0.2.1` | [wqty123/dsh-browser](https://github.com/wqty123/dsh-browser) `dsh-builtin-browser@0.4.2` |
|---|---|---|
| 一句话 | 自包含的**无头浏览器运行时**（Playwright/Patchright + OpenCLI 作为自身依赖打包） | **共享真实浏览器**：agent 驱动一个可见、人可随时接管的浏览器（"人机同页"） |
| 对外服务 | `ctx.provide('browser', BrowserService)` | `ctx.browser` **seam** + 自家 `browser-electron` provider（API 形状不同） |
| 工具面 | `browser_index` + `browser_call` 两个（渐进披露，常驻约 325 token）；`flat` 模式才展开 34 个 | 34 个 `browser_*` 工具**常驻** |
| 默认可见性 | `headless: true` | 可见窗口；桌面端 = 官方侧栏那一个页面 |
| 登录态 | `storageStatePath`/`authProfiles`（按域名授权，默认只读不回写） | 复用侧栏 partition 的真实登录态，`browser_auth` 可导出 |
| 平台覆盖 | 靠 **OpenCLI**：小红书/推特/Reddit/IG/FB 等社交 adapter | 通用的真人可见浏览，**无 OpenCLI 社交 adapter 概念** |
| 桌面端代价 | 无，不碰安装目录 | 需 `node desktop-bridge/install.mjs` **改已安装桌面端 `resources/app/` 的 main.js**；桌面端升级后被覆盖、必须重跑 |
| 额外依赖 | Chromium 内核复用 `%LOCALAPPDATA%\ms-playwright`（约 400MB，`runtime.install` 补） | 依赖 **electron**（44+ 需 `npx install-electron`，约 100MB）＋ `resources/app/` 的 bridge |
| peer（本机 0.2.0-rc.2） | `>=0.2.0-rc.2 <0.2.1-0` ✅ 正对口 | `>=0.1.1-rc.2 <0.3.0` ✅（表里在 0.2.1-alpha.1 验证过，0.2.0-rc.2 亦有实测记录） |
| 生态数据 | 27 ★ / 8818 下载(30d) | 100 ★ / 15051 下载(30d) |
| 已声明的边界 | Cookie 明文落盘；Patchright 禁用 Playwright console API | CAPTCHA 需人工接管；装进桌面 profile 后 agent 可读侧栏所有页面内容与 Cookie；`browser_restrict` 只是模型自设的软护栏 |

## 二、决定性差异：web-search-pro 只认 anweat 的服务

这不是偏好问题，是本地代码写死的：`dsh-web-search-pro` 编译期就 import 了 anweat 的类型——[browser-service.d.ts:7-8](C:/Users/liveu/.dsh/profiles/desktop/node_modules/dsh-web-search-pro/lib/types/browser-service.d.ts)：

```ts
import type { BrowserService as DshBrowserService } from '@anweat/dsh-browser';
export type BrowserService = Pick<DshBrowserService, 'render' | 'snapshot' | 'searchResults' | 'opencli' | 'close' | 'observe' | 'listTargets' | 'sessionState'>;
```

运行期还会做完整度自检（[browser-access.js:68](C:/Users/liveu/.dsh/profiles/desktop/node_modules/dsh-web-search-pro/lib/browser-access.js)）：`['render','snapshot','searchResults','opencli']` 有一个不是函数，就判 `state: 'incomplete'`，理由写的是 `dsh-browser lacks …; update @anweat/dsh-browser`。它实际调用的就是这几个方法：`browser.render`（`lib/fetch.js:337`）、`browser.searchResults`（`lib/engines.js:647,668`）、`browser.opencli`（`lib/engines.js:505`）、`browser.snapshot`（`lib/actions/read.js:182`）。

`dsh-builtin-browser` 的 seam 是给**它自己的** provider 注册用的（会话生命周期/错误码），既不实现这套方法，也照样占着 `browser` 这个服务名。所以：

- 只装 `dsh-builtin-browser` → web-search-pro 的 11 个浏览器类平台（xiaohongshu/twitter/reddit/zhihu/weibo/douyin…）**仍然不可用**，只是错误文案从"未安装"变成"服务不完整"。
- 两个都装 → 两个插件都想 provide `browser`，大概率撞服务（这一点我没实测，属于读架构的推断）。

另外注意 `dsh-builtin-browser` 那个 `desktop-bridge/install.mjs` 改的是 `C:\Programs\AITech\DeepSeekHarness\resources\app\main.js`——本仓库已经有若干针对桌面端的补丁脚本，再叠一个会在每次桌面端升级后失效，维护成本你要算进去。

## 三、建议

- **你的目的（让 web-search-pro 的中文社区/社交平台可用）→ 装 `@anweat/dsh-browser@0.2.1`**，就是你上一步在 GUI 市场里准备点的那个。装完重启，补 Chromium 内核（`runtime.install`，或在插件设置里用 `executablePath` 把 400MB 挪到别的盘），然后跑 `web_call sources.status` 看那 11 个平台是否转 ready。
- **`wqty123/dsh-builtin-browser` 解决的是另一个问题**：你要亲眼看着 agent 操作浏览器、CAPTCHA 时自己接管、或者要用侧栏里已登录的那个真实会话。它不是 web-search-pro 的后端。真想要这个能力，建议**单独一个 profile**（比如 `web`）装它，避免和 desktop 里的 `browser` 服务打架。
