## 2. 两个搜索插件怎么分工最好

先说结论：**搜索交给 free-search，抓取交给 web-search-pro，证据包用显式工具调**。也就是把刚写入的那份补丁里的 `searchProvider` 从 `web-search-pro` 换成 free-search 的 provider id `ddg`：

```yaml
- id: web-search-pro
  name: "dsh-web-search-pro"
  config:
    registerProvider: true          # 只为了注册 fetch provider
- id: web
  name: "@deepseek-ai/dsh-web"
  config:
    searchProvider: ddg             # ← free-search：22 引擎 + 无 key 兜底 + 失败冷却
    fetchProvider: web-search-pro   # web_search-pro：正文裁剪 + offset 续读 + 缓存
```

为什么这样分，依据都在源码里：

- `dsh-free-search/lib/index.js:3160` 里 provider id 就是 `"ddg"`，而且它**只注册 search**；同一文件 `:3578` 写着：`if (!ctx.web.searchProviderId || ctx.web.searchProviderId === OFFICIAL_SEARCH_PROVIDER_ID)` 才把自己顶上去，否则 `:3586` 只打一条 warn —— `free-search: search is served by provider "..." , not "ddg" — web_search will NOT use this plugin.`。所以显式 pin `ddg` **既不会触发它改写、也不会触发这条 warn**，等于用一行配置把"搜索归谁"钉死，三个插件的默认行为都不再互相猜。
- web-search-pro 在 `lib/index.js:108-110` 一次注册两个：`web.registerSearchProvider(...)` + `web.registerFetchProvider(...)`，id 都是 `web-search-pro`。它的 fetch 端有正文裁剪和 `[Continue with ... offset=N]` 续读（宿主自带的 `http` fetch 没有）；search 端有证据评分/引用包。这两样是"加工"，而 free-search 是"广度"（22 个引擎，且 exa/tavily/keenable/firecrawl/parallel 都有免 key 通道）。

三种配法对比：

| 配法 | `web_search` 走 | `web_fetch` 走 | 代价 |
|---|---|---|---|
| A（推荐）`ddg` + `web-search-pro` | free-search | pro 的裁剪/续读 | 依赖 free-search 在装 |
| B（当前已写入）两个都 `web-search-pro` | pro（证据包） | pro | 默认搜索丢掉 free-search 的引擎面与免 key 兜底 |
| C `registerProvider: false` | free-search | 宿主 `http` | 抓取没有裁剪与续读 |

无论哪种配法，**`web_index` / `web_call`（证据管线）和 free-search 的 5 个工具（`multi_search` / `advanced_search` / `platform_search` / `video_search` / `free_search_test`）都照常在**——它们是工具，不靠宿主 provider 路由。所以"要证据包"时永远可以直接 `web_call search.run` / `web_call read.fetch`，跟谁当 provider 无关。

唯一要接受的代价：pin 了 `ddg` 之后，哪天把 free-search 卸了/禁用了，`web_search` 会直接报 provider 未注册（这正是 free-search 自己不肯写死 pin 的原因，issue #51 那个悬空引用的老毛病）。想避开就维持配法 B。

**要我把 `searchProvider` 改成 `ddg` 吗？** （一行改动，仍然要重启 DSH 才生效；回退就是覆盖那个 .bak。）

## 3. web-search-pro 需要浏览器插件吗？——不需要，是刻意不依赖

`dsh-web-search-pro/lib/index.js:33-36` 的注释把话说明白了：

> `browser` (dsh-browser) is deliberately NOT injected: Cordis 4.0.4 treats every `inject` entry as required (the fiber stays PENDING until it exists) and has no optional form. It is read per call with `ctx.get('browser')` instead.

对应代码：`:36` / `:141` `export const inject = ['tools', 'systemPrompt'];`（**没有 browser**），`:63` `const getBrowser = () => ctx.get('browser')`——每次调用时惰性取。所以 `@anweat/dsh-browser` 只是 peerDependency，缺了它插件照样激活、照样注册 provider。

没装浏览器丢的只是那批**浏览器类源**：xiaohongshu / twitter / reddit / instagram / facebook / zhihu / weibo / douban / tieba / douyin / kuaishou（`web_call sources.status` 里它们显示 `[missing]`，同一个工具里还有一行 `browser:dsh-browser [missing]` 就是这个）。其余十几个源不受影响：seam、exa、ddg、bing、github、v2ex、rss、arxiv、pubmed、wikipedia、hackernews、stackexchange、openalex、semanticscholar、anysearch、tavily。另外两条也顺带澄清：`bilibili` 缺的是 `cli:bili`、`youtube` 缺的是 `yt-dlp`，跟浏览器插件是两回事。

所以第 ① 项那份接管补丁**不装浏览器也能生效**；要让那 11 个平台源可用，才需要 `@anweat/dsh-browser`。
