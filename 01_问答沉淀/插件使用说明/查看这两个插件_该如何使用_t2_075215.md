## 三、DSH 侧：key 已经在生效（含一处自我更正）

我一开始想用 agent shell 验证 DSH 能否读到这些变量，第一次拿到的是**假信号**（六个全 False）。进一步对比才发现原因——**DSH 给 agent 的 shell 做了密钥脱敏**：`HKCU\Environment` 的 20 个变量里这个 shell 只看得见 11 个，被抹掉的 9 个恰好是 `AGNES_API_KEY`、`EXA_API_KEY`、`FIRECRAWL_API_KEY`、`OPENROUTER_API_KEY`、`TAVILY_API_KEY`、`OBLIVION_BRIDGE_TOKEN`、`HTTP_PROXY`、`HTTPS_PROXY`、`SSL_CERT_FILE`（按 KEY/TOKEN/PROXY/CERT 过滤）。**所以不能用 agent shell 的 env 判断 DSH 读不到 key。**

旁证来自插件自身：web-search-pro 报 `exa credential=configured`、`tavily credential=configured`，而它的 Exa 没有无 key 通道（`cli:mcporter [missing]`）→ DSH 进程确实拿得到这两个 key。加上实测 exa / tavily / firecrawl / parallel 四个引擎全 OK，结论就是同一批 User 变量，DSH 已在用。

**但要更正"OK 即代表有 key"这个推断**：[free-search lib\index.js:3296-3321](<C:/Users/liveu/.dsh/profiles/desktop/node_modules/dsh-free-search/lib/index.js>) 里这四个引擎都有无 key 通道——exa 走 Exa MCP、tavily 走匿名额度、firecrawl 走官方匿名额度、parallel 走 keyless MCP。**所以 parallel 能跑恰恰是因为它没有 key。** 真正"无 key 直接跳过"的是：perplexity、deepseek-official、serpbase、serply、youcom、baidu、kimi、aliyun、doubao、zhihu、openai、gemini、claude。

## 四、要不要动

- **什么都不用做**：exa/tavily/firecrawl/parallel 已可用；Agnes 也已接在 DSH 的 LLM provider 上（profile `agnes`，apiKeyEnv `AGNES_API_KEY`）。
- **想补更多引擎**（perplexity / youcom / baidu / kimi / aliyun / doubao / zhihu）：opencode 里也没有这些 key。最省事是加 User 环境变量后**重启 DSH**（DSH 在启动时从注册表继承，启动后改注册表不生效）；也可以走 Web Search Pro / Free Search 的设置面板填入，那会写进凭据中心或条目 config——优先级更高：`凭据中心 → 条目 config 的 <x>ApiKey → process.env`。
