# 通过搜索，查看如何从观影者 · 轮 25

- 来源会话: `session-235265a4-9730-444a-9249-72d5aca7f984`

## 问题

relauncher 拉起 + 冷启动和app.relaunch() + 冷启动全套相比的区别在哪

## 回答

## 结论

差别只在**“旧实例怎么走、新实例谁拉”**这两点；**冷启动那一段（全量插件加载 + Web 服务 + Provider 初始化）两者完全一样**，所以启动耗时没有区别。真正的差异是：`app.relaunch()` 走**优雅退出后自我拉起**（参数/环境原样保留），relauncher 走**强杀后由游离 cmd 拉起**（无参数、无刷盘）。

## 方案对比

| 维度 | relauncher `start` + 冷启动（现在的快速路径） | `app.relaunch()` + 冷启动（优雅路径） |
| --- | --- | --- |
| 谁拉起新实例 | 游离 `cmd`（WMI 创建，绕开 Electron job object，否则一起被端掉） | Electron 自己：`app.relaunch()` 记录 execPath+argv，退出时由主进程 spawn |
| 旧实例怎么退出 | `Stop-Process -Force` 直接终止：**不 dispose 插件、不刷会话** | `app.quit()` → `before-quit` → 活动任务确认（有才弹）→ `finishQuit`（先隐藏窗口）→ `backend.close()` 顺序 dispose + 刷盘 → 再 spawn |
| 启动参数/环境变量 | `start "" "%APP%"` **不带参数**；环境继承 cmd | **原样复用**当前进程的 execPath、argv、env（DSH 桌面端无自定义参数，实际等价） |
| 单实例锁/端口 | 先轮询镜像消失再加锁启动 → 无冲突 | 退出完成后才 relaunch → 天然无冲突 |
| 冷启动耗时 | 一样（都全量加载插件、起 Web 服务、初始化 Provider） | 一样 |
| UI 体感 | 面板已做成"点完即隐藏"→ 秒关，后台杀+拉起 | `finishQuit` 第一步 `mainWindow.hide()` → 也是秒关，但前面可能先弹"有活动任务"确认 |
| 数据风险 | 丢最后未落盘增量；按路径/镜像名杀进程可能误伤第二个同路径实例 | 最低（会话与插件状态完整落盘） |
| 失败模式 | relauncher 起不来/start 失败 → 应用停在关闭态 | 确认被取消/退出被阻塞 → **不会** relaunch |
| 典型使用场景 | 卡死、改代码后快速生效、确实不介意丢一点增量 | 正常退出、更新安装、需要保数据 |

## 要点

- **`app.relaunch()` 的本质**：不是"现在再开一个"，而是把"退出后重新执行当前命令"记在 app 对象上，`app.quit()` 真正退出时才 spawn —— 所以它天然与优雅关闭绑定，且参数/环境无损。
- **relauncher 的本质**：一个外部守护批处理，等旧进程全消失再 `start` exe —— 它是"强杀 + 冷启"的组合，不能替你把旧实例优雅收尾。
- **启动侧没有捷径**：两个路径都要付同样的冷启动（约等于"打开应用"的耗时）；今天两次重启的 web-boot 组合包失败也是启动侧的问题，与用哪条重启无关。

## 盲区

- 两者在"新实例的父进程/窗口置顶顺序"上略有差异（relauncher 的实例由 cmd 拉起后 cmd 退出），对 DSH 行为无影响，未逐项实测。
- `app.relaunch()` 若带 `execPath/args` 覆盖（Electron 允许），可以模拟任意启动方式；当前 DSH 未使用自定义参数。
