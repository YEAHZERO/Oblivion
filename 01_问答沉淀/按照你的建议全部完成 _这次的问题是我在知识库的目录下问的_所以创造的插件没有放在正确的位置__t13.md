## 关键发现：你的 0.1.20 **没有 provide 任何服务**

`src/index.ts` 里 `export const inject = ['tools', 'systemPrompt', 'agents']` —— **只有 inject，没有 provide**。它把能力注册成：

- `systemPrompt.section(...)` — 提示词段落
- `tools.register(...)` — 7 个工具（`registerTools`）
- 内部模块间靠**闭包变量**传递（`knowledge` / `profile` / `graph` / `stats` / `digest` / `perspective` 直接传给 `registerQaLoop`、`registerTools`）

**这意味着我的 http-bridge 无法通过 `ctx.get('oblivion')` 拿到 core 的门面**——因为根本不存在这个服务。我之前那套能跑通，是因为我自己写了 `provide`。

## 所以桥接只有两条路

**路线 A：core 暴露服务（改 core）**

在 `src/index.ts` 的 `apply` 末尾加：

```ts
ctx.provide('oblivion', { knowledge, profile, graph, stats, digest, perspective })
```

然后 http-bridge 用 `inject: ['webServer','oblivion']` + `ctx.get('oblivion')`。

- 优点：干净、符合 Cordis DI 惯例、桥接层可替换
- 代价：**要改你的 0.1.20 源码**，版本升到 0.2.0，走一遍 build/selfcheck/version bump

**路线 B：桥接层直接用 core 的工具出口（不改 core）**

http-bridge 不调 core 内部函数，而是**把 MCP 的 `tools/call` 转成 DSH 的 `tools` 调用**——即桥接层调用 `ctx.tools` 里已注册的 `oblivion_search` / `oblivion_capture`。

- 优点：**零改 core**，core 的 7 个工具自动全部可达（不用为每个工具写一遍适配）
- 代价：要弄清 `ctx.tools` 的调用 API（`tools.invoke(name, args)` 之类），且要处理「工具在 agent 作用域层注册」的问题——`registerTools` 既注册到根 `toolsCtx`，也注册到每个 agent 的 scope，**桥接层拿到的可能是空的根层**（因为分层是覆盖语义，agent 层才有）

**路线 B 有个真实风险**：`installForAgent` 用 `agentCtx.inject(['systemPrompt','tools'], ...)` 把工具注册进 **agent 作用域**。http-bridge 挂在 profile 插入行下，**不在任何 agent 链上**——按你自己在注释里写的规则（`scopeTarget`），它可能看不到那些工具。这跟你踩过的 `agents` 坑是同一类。
