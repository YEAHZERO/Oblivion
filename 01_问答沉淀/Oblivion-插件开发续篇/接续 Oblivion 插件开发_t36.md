## 问题

前三张的"上下文"插件和第四章的"上下文"有什么区别？然后前三张的看了有什么作用？

## 回答

看清楚了。这两个"上下文"是完全不同的东西：

## 前者：Oblivion 上下文监控面板（只读观测）

截图 1-3 显示的是 **Oblivion Panel** 挂载的上下文观测界面，纯**可视化 + 统计**：

| 功能 | 内容 |
|---|---|
| **Token 统计** | 系统提示词、工具定义、用户消息、注入内容、助手消息、工具结果各占多少 token |
| **上下文窗口** | 当前 409.8k / 512.0k = **80% 已用**，实时进度条 |
| **上下文趋势图** | 整个会话的历史增长曲线，能看到每次工具调用后上下文跳涨 |
| **文件活动 / 命令执行** | 最近改了什么文件、跑了什么命令、耗时多少 |
| **会话累计** | 总轮次 33、总步数 284、工具调用 511 次 |

**作用**：让你**看见**上下文正在发生什么——哪些内容占地方、哪里在涨、工具调用花了多少 token。是诊断工具，不是干预工具。

## 后者：billion-context 压缩引擎（实际干活）

截图 4 是 **billion-context** 插件自己的面板，这是**真正在处理上下文**的组件：

| 指标 | 数值 | 含义 |
|---|---|---|
| 请求总数 | 1.5K | 总共发了多少次 LLM 请求 |
| 压缩累计节省 | **1.61B** | 压缩帮你省了 16 亿 token |
| 净节省 | **1.61B** | 实际少发的 token |
| 全局缓存命中率 | **94.0%** | 94% 的 token 命中缓存，不用重发 |
| 输入 token | 141.2M | 实际发给模型的输入 |
| 缓存命中 token | 132.5M | 其中 94% 是缓存复用的 |

**作用**：在 LLM 请求发出之前，**主动压缩历史上下文**，把不必要的旧内容折叠掉，节省 token 和延迟。这是**干预层**，直接改变发给模型的内容。

## 关键区别

```
┌─────────────────────────────────────────────────┐
│  billion-context（中间件层，透明拦截）           │
│  ┌───────────────────────────────────────────┐  │
│  │ 原始历史 → 压缩 → 实际发送的上下文        │  │
│  │          ↓                                │  │
│  │ 节省 1.61B token，命中率 94%              │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────────┐
│  Oblivion 上下文面板（观测层，只读）             │
│  显示：当前用了多少 / 谁占了大头 / 趋势如何     │
│  → 只读，不干预                                  │
└─────────────────────────────────────────────────┘
```

**简单说**：billion-context 是**压缩引擎**（在后台默默干活省钱），Oblivion 上下文面板是**仪表盘**（告诉你钱省了多少、现在油表剩多少）。两者配合使用。
