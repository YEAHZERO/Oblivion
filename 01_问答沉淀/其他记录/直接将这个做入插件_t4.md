## 两个文件夹分析结论

### 1. `deepseek-pp-shell-host`（v1.14.0，npm 包）

**定位**：DeepSeek++ 浏览器扩展的 **Native Messaging Shell MCP 宿主**（Apache-2.0，Node ≥18.17）。

架构分层很干净：

| 层 | 文件 | 职责 |
|---|---|---|
| CLI | `bin/deepseek-pp-shell-host.mjs` → `lib/installer.mjs` | `install` / `status` / `uninstall`，写浏览器清单 + Windows 注册表 |
| 安装 | `lib/installer-locations.mjs`、`lib/host-files.mjs`、`lib/officecli-installer.mjs` | 三平台路径解析；把 `native/` 复制到 `%LOCALAPPDATA%\DeepSeek++\NativeHost`，生成 `.bat` 包装器 |
| 协议 | `native/contracts.mjs` | MCP `2025-06-18`；11 个工具的完整 JSON Schema；上限常量集中在此 |
| 传输 | `native/framing.mjs` | Chrome 原生消息 4 字节 LE 长度前缀；1 MB 上限（issue #297） |
| 路由 | `native/router.mjs` | `initialize` / `tools/list` / `tools/call` |
| 调度 | `native/runtime-dispatcher.mjs` | **工具调用串行化**（`toolCallTail`），通知不排队 |
| 能力 | `process-provider` / `file-provider` / `skill-provider` / `picker-provider` / `session-provider` / `os-adapter` | shell、Python、本地技能预览、文件夹选择、常驻会话 |

**三个最值得抄的设计**：

1. **常驻会话用哨兵而非 PTY**（`contracts.mjs:41-55`）。单一 `.mjs` 无 `node_modules`，引 `node-pty` 就得按平台带预编译二进制。改成 `child_process` + 随机结束标记 `__DPP_SESSION_END__`，让 OfficeCLI 这类常驻工具跨调用存活。代价是输出里的标记串需要转义。
2. **工具调用串行、其它消息并行**（`runtime-dispatcher.mjs:13-27`）。shell 会话有状态，并发工具调用会互相污染；用一条 Promise 链把 `tools/call` 串起来，`initialize` 不排队。
3. **错误必须带原请求 id**（`runtime-dispatcher.mjs:38-41`）。否则扩展侧按 id 匹配不到，只能等超时，用户看到的是卡死而不是报错。

**局限**：`shell_exec` 无沙箱、无审批、无路径限制；`local_file_read` 能读 `~/.ssh`。安全边界**完全依赖浏览器扩展侧的授权 UI**，宿主自己不设防。这是它和 DSH 权限模型最大的哲学差异。

### 2. `deepseek-plus-plus-1.0.2-edge`（WXT 打包的 MV3 扩展）

**定位**：DeepSeek 网页版的**增强客户端**。`manifest.json` 暴露了全貌：

- 权限：`storage alarms nativeMessaging contextMenus offscreen debugger tabs sidePanel`
- 注入：`content-scripts/content.js`（491 KB，isolated world）+ `main-world.js`（312 KB，`world: "MAIN"`，为了改页面原生的 `fetch`/`WebSocket`）
- 载体：`background.js` **1.02 MB 单文件**（WXT/Vite 把整个 service worker 打成一块）；`chunks/` 是 sidepanel 的懒加载路由（`CapabilitiesPage`、`ChatPage`、`SettingsPage`、`LibraryPage`、`ProjectsPage`）
- 沙箱：`sandbox-runner.html` + 独立的宽松 CSP（`unsafe-eval`、`blob:` worker），配合 `pyodide/`（9.6 MB wasm）在本地跑 Python
- 资源：`pet/deepseek-whale-pet-states.png`（632 KB 雪碧图）、`deepseek/sha3_wasm_bg.wasm`

**桥接机制**（`background.js`，`connectNative` 处）：

```js
function oa(e){
  if(!chrome.runtime?.connectNative) throw new V('mcp_native_messaging_unavailable', ...)
  let n = chrome.runtime.connectNative(e)          // e = 'com.deepseek_pp.shell'
  ...
  n.onMessage.addListener(e => { ... pendingRequests ... })
}
```

`background.js:285` 那段是给模型看的 **shell 能力提示词**（`shellHintTitle` / `shellHintExec` / `shellHintStatus`），说明扩展会把工具说明注入 DeepSeek 页面，让模型输出 XML 工具标签，由扩展拦截、转发到 native host。

**关键差异——它走 nativeMessaging，不是 HTTP**。这意味着你的插件要接进去，有两条路：

| 路径 | 优点 | 缺点 |
|---|---|---|
| 扩展改代码加 native host | 与现役一致 | 要改 1 MB 的 `background.js`，且需重新分发扩展 |
| **DSH 侧起 HTTP MCP 端点** | 不动扩展的 native 部分，扩展只要加一条 `streamable_http` MCP 配置 | 需要扩展支持自定义 MCP 传输（`CapabilitiesPage` 里的 `native_messaging` / URL 分支已经暗示支持） |

`CapabilitiesPage-DFI-d_Vx.js` 里有 `e.transport.kind !== 'native_messaging'` 的分支和 `Re(e.transport.url)` 校验，说明**扩展已经支持 HTTP MCP 传输**。这就是我选第二条路的依据。
